# 기능 기획 — 가족 케어 + 채팅 (Family Care & Chat)

> 반려는 혼자가 아니라 **가족이 함께** 돌본다. 가족 그룹으로 "오늘 누가 밥·물·산책을 챙겼는지"를 공유해 **이중 급여·산책 누락**을 막고, 가족 채팅으로 반려 소통을 앱 안으로 모은다 — Pawloop(포루프)의 **일일 사용 이유(retention)**를 만드는 기능.
>
> 관련 문서: [비전](./vision.md) · [페르소나](./personas.md) · [기능 명세](../01-design/feature-spec.md) · [ERD](../03-database/erd.md) · [API 명세](../04-api/api-spec.md)

## 1. 배경 & 문제 정의

Pawloop의 기존 축(산책 트래킹·동반장소 지도·커뮤니티)은 "반려인 1명"을 전제한다. 그러나 실제 반려 가정의 다수는 **여러 가족 구성원이 한 마리를 나눠 돌본다**. 케어가 구성원 개인의 기억과 단톡방에 흩어져 있어, 매일 반복되는 실패비용이 쌓인다.

| 문제 | 무슨 일이 벌어지나 | 실패비용(왜 아픈가) |
| --- | --- | --- |
| **이중 급여** | 엄마가 아침에 밥을 줬는데, 퇴근한 딸이 모르고 또 준다. 반대로 "누가 줬겠지" 하고 아무도 안 주기도 한다. | 과식·비만·건강 문제, 또는 굶는 반려견. "밥 줬어?"를 매번 물어야 하는 확인 비용. |
| **산책 누락** | "오늘 산책 나갔었나?"를 아무도 확신 못 함. 서로 상대가 시켰다고 생각해 하루가 통째로 빠진다. | 운동량 부족이 **기록 없이** 누적. 산책 wedge(비전 문서)의 데이터가 가족 단위에서 구멍 난다. |
| **소통 비용** | 물 갈아주기·약·병원 일정·산책 시 주의사항("리드줄 짧게", "공사 구간 피하기")이 카톡 단톡방·구두 전달에 흩어짐. | 전달 누락·중복 질문. 반려 관련 대화가 앱 밖에 있어 Pawloop을 열 이유가 줄어든다. |

**핵심 통찰**: 케어의 단위는 개인이 아니라 **가족**이다. "누가·언제 했는지"가 한 곳에 보이기만 해도 이중 급여와 누락은 대부분 사라진다. 그리고 이 확인 행동("오늘 케어 어떻게 됐지?")은 **하루에도 여러 번 반복**되므로, 산책과 함께 Pawloop의 두 번째 일일 사용 이유가 된다.

## 2. 가치 제안 (Value Proposition)

| 대상 | 제공 가치 |
| --- | --- |
| **가족 구성원** | 오늘의 케어(물·밥·산책)를 **누가·언제 했는지** 한눈에 — 묻지 않아도 알고, 중복·누락이 사라진다. |
| **반려견** | 급여·산책이 가족 단위에서 빠짐없이 관리되어 건강 루틴이 안정된다. |
| **Pawloop 제품** | ① 케어 확인이라는 **고빈도 재방문 이유** → retention ② 가족 초대 = **자연스러운 바이럴 루프**(1명이 쓰면 가족 전원이 가입) ③ 케어 로그는 post-MVP 건강·식사 로그 확장(비전 문서)의 기반 데이터. |

한 줄 정의: **"우리 집 반려 케어 상황판 + 가족 단톡방"** — 가족이 같은 화면을 보고, 같은 곳에서 대화한다.

## 3. 사용자 시나리오 (가족 구성원 시점)

### S1. 퇴근한 딸 — "밥 또 주기 전에 확인"

> 저녁 7시, 퇴근한 지은은 배고파 보이는 보리에게 밥을 주려다 Pawloop **홈의 오늘의 케어 카드**를 먼저 연다. `밥 — 엄마 · 오후 5:30 완료`가 보인다. 이중 급여를 피하고 대신 아직 비어 있는 `물 갈아주기`를 하고 완료 체크. 카드에 자신의 이름과 시각이 남아 가족 모두가 즉시 안다.

### S2. 아빠 — "산책 나가기 전 주의사항 확인"

> 주말 아침, 평소 산책 담당이 아닌 아빠가 보리를 데리고 나가기로 한다. **family_screen**의 오늘 케어 현황에서 `산책 — 미완료`를 확인하고, **산책 시 주의사항** 메모에서 "아파트 후문 공사 중 — 정문으로 나갈 것, 리드줄 짧게"를 읽는다. 산책 후 `산책` 완료를 기록하니 가족 케어 현황에 바로 반영된다.

### S3. 엄마 — "가족 초대와 채팅으로 병원 일정 조율"

> 엄마가 가족 그룹을 만들고 **초대코드**를 가족 단톡방에 공유 → 아빠·지은이 코드 입력으로 참여, 멤버 목록에 3명이 뜬다. 보리 예방접종이 다가오자 엄마는 **가족 채팅(family_chat_screen)**에 "토요일 오전 병원 누가 갈 수 있어?"를 올리고, 지은이 답해 일정이 정해진다. 반려 관련 대화가 케어 현황과 같은 앱에 모인다.

## 4. 기능 범위 — MVP vs post-MVP

### MVP

| # | 기능 | 내용 | 비고 |
| --- | --- | --- | --- |
| 1 | **가족 그룹** | 그룹 생성 · **초대코드**로 참여 · 멤버 목록(owner/member) | `POST /api/groups` · `POST /api/chat/rooms/{roomId}/invites`(코드 발급) · `POST /api/chat/invites/{code}/join`(참여) · `GET /api/groups/me` |
| 2 | **오늘의 케어 공유** | 물 갈아주기·밥·산책 완료 여부 + **누가·언제** 했는지 기록/조회 | `GET|POST /api/groups/{groupId}/care-logs` · 홈에 오늘의 케어 카드 |
| 3 | **산책 시 주의사항** | 가족 공유 메모(예: 공사 구간·리드줄) 조회/수정 | `GET|PUT /api/groups/{groupId}/walk-notes` |
| 4 | **가족 채팅** | 그룹 채팅(커서 페이지네이션) — MVP는 **폴링** 기반 | `GET|POST /api/chat/rooms/{roomId}/messages` — 방은 가족 그룹 종속이 아니라 범용 리소스다(ADR-0011). 커서는 `id` 가 아니라 방별 `room_seq` |

### post-MVP

| 기능 | 내용 |
| --- | --- |
| **친구 추가** | 가족 외 반려인 연결(동네 산책 친구 등) |
| **케어 알림/리마인더** | "저녁 산책 아직 안 나갔어요" 등 미완료 케어 알림 |
| **케어 히스토리 통계** | 누가 얼마나 돌봤는지 기간별 집계·회고 |
| **실시간 푸시** | 채팅·케어 실시간 반영(WebSocket/STOMP) — MVP 폴링을 대체 |

> 데이터 모델(추가): `family_group` · **`chat_room`·`chat_room_member`·`chat_room_invite`** · `chat_message` · `walk_note` (**`group_member` 는 만들지 않았다** — 멤버십 표는 `chat_room_member` 하나이고, 방이 `origin_kind`/`origin_ref` 쌍으로 그룹을 불투명하게 가리킨다. ADR-0011), 그리고 기존 계획의 `care_log` 확장(`group_id` nullable, `type[water|meal|walk|med|vet]`, `done_by`, `occurred_at`, `memo`). 상세는 [ERD](../03-database/erd.md)·[스키마](../03-database/schema.md) 반영 예정.
>
> 프론트: 홈 오늘의 케어 카드 + `family_screen`(멤버·초대코드·케어 현황·주의사항·채팅 진입) + `family_chat_screen`. **더미가 아니라 서버 연동이다.** 가족·케어의 SSOT 는 `app/lib/v2/data/family_repository.dart`(`ServerCareType`·`CareLogEntry`·`WalkNoteSheet`, #76), 채팅은 `app/lib/v2/data/chat_repository.dart`(#81). `pet.dart` 에 남은 것은 아이콘·색 팔레트뿐이고 `ChatMessage`·`kChatMessages`·`kChatRooms` 는 삭제됐다 — **그 자리에 "다시 만들지 말 것" 경고가 있다.** 서버 계약의 케어 종류는 `CareType` 이 아니라 `ServerCareType` 이다(이름이 겹치니 주의). UI는 기존 바이브 유지 — AuroraBackground · GlassCard · 따뜻한 그라데이션(#FFA96B→#FF7E8A) · Pretendard · Fluent 이모지 톤.

## 5. 성공지표 (Success Metrics)

가족 케어가 "일일 사용 이유"가 되는지는 **"그룹 형성 → 매일 기록 → 대화 정착"** 흐름으로 판단한다.

| 단계 | 지표 | 왜 보는가 |
| --- | --- | --- |
| **형성(Adoption)** | 가족 그룹 생성률, 초대코드 참여 전환율, 그룹당 평균 멤버 수 | 초대 루프가 실제로 도는가(바이럴 검증) |
| **참여(Engagement)** | 그룹당 일일 케어 기록 수(물·밥·산책), 케어 카드 조회 빈도 | "확인하러 매일 연다"가 성립하는가 |
| **소통(Communication)** | 주간 채팅 메시지 수, 주의사항 메모 작성·수정 수 | 반려 대화가 단톡방에서 앱으로 이동하는가 |
| **유지(Retention)** | 그룹 소속 사용자 vs 미소속 사용자의 W1/W4 리텐션 차이 | 가족 기능이 retention을 실제로 끌어올리는가 (핵심 검증) |
| **문제 해결(Outcome)** | 케어 3종(물·밥·산책) 일일 완료율, 산책 누락일 감소 | 이중 급여·누락이라는 원 문제가 줄어드는가 |

> 위 수치 기준은 확정 KPI가 아니라 **검증할 가설**이며, 실데이터 확보 후 목표치를 설정·조정한다. 그룹 소속 사용자의 리텐션 우위가 확인되면 온보딩에서 가족 초대를 전진 배치한다.

## 6. 리스크 & 대응

| 리스크 | 내용 | 대응 |
| --- | --- | --- |
| **1인 가구에는 무용** | 혼자 돌보는 반려인에게 가족 그룹은 빈 기능 — 타겟 일부만 해당. | 그룹 미생성 시에도 오늘의 케어 카드는 **개인 케어 체크**로 동작하게 설계(`care_log.group_id` nullable). post-MVP 친구 추가로 확장. |
| **폴링 채팅의 한계** | MVP 채팅은 폴링이라 즉시성이 떨어지고, 주기가 짧으면 서버 부하. | 커서 페이지네이션으로 증분만 조회, 폴링 주기 보수적으로 시작. 지표가 검증되면 WebSocket/STOMP(post-MVP)로 전환. |
| **동시 기록 충돌** | 두 가족이 거의 동시에 같은 케어(밥)를 기록 → 이중 급여를 막으려던 기능이 중복 기록을 만든다. | 기록 전 오늘 현황을 항상 먼저 노출(확인→기록 순서 유도), 같은 타입의 최근 기록이 있으면 확인 안내. |
| **알림 부재로 가치 반감** | MVP엔 리마인더·푸시가 없어 "앱을 열어야만" 상황을 안다 — 누락 방지 효과가 제한적. | 홈 최상단 오늘의 케어 카드로 앱 진입 즉시 노출. 케어 알림은 post-MVP 최우선 후보로 지정. |
| **초대코드 유출·프라이버시** | 코드가 노출되면 제3자가 그룹에 들어와 케어 현황·채팅을 볼 수 있다. | 초대코드 재발급 가능하게 설계, 멤버 목록에서 owner가 확인·관리(상세 정책은 API 명세에서 확정). |
| **백엔드 선행 필요** | **해소됨**(#76·#79·#81). ~~프론트는 더미(`kCareToday` 등)로 먼저 가지만, 실가치는 가족 간 **실시간 공유**라 백엔드 연동 전까지 검증 불가. | API 4종(그룹·케어·채팅·메모)을 [API 명세](../04-api/api-spec.md)에 추가하고 로드맵에서 로그인 연동 이후 단계로 배치. |
